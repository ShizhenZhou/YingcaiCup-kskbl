# 屏幕显示子系统（ST7789 1.54" SPI）

> 记录日期：2026-09-21 起
> 屏幕型号：**1.54" 彩色 IPS 8 针模块**（ST7789V / 240×240 / 4 线 SPI）
> 连接方式：**直连 ROCK 5B+ 40-pin**，**不使用任何额外控制器**

---

## 0. 为什么改成"屏幕直连"

原方案是「ROCK → 串口 → ESP32 → WS2812B 灯带」。改用 SPI 屏直连后：

| | 原方案（ESP32 + 灯带） | **新方案（SPI 屏直连）** |
|---|---|---|
| 额外芯片 | ESP32（可编程，**规则上有解释成本**） | **无** ✅ |
| 代码分布 | Python + Arduino C++ | **100% Python** ✅ |
| 通信协议 | 需要自己设计串口帧格式 | SPI 标准接口，无需协议 |
| 视觉表现 | 只能表达亮度/颜色/节奏 | **能显示频谱、波形、文字、图片** ✅ |
| 调试复杂度 | 两个设备、两套工具链 | 一个进程 ✅ |

**"屏幕显示什么"比"灯怎么亮"信息量大得多**，而且能直接把"变声改变了频率分布"这件事可视化给评委看。

## 2. 接线表

> ✅ **2026-09-23 已按本表接好 8 根杜邦线并成功点亮**（纯色 / 彩条 / 渐变 / 中英文字全部通过）。
>
> ⚠️ **屏幕丝印必须「按名字对」，不要「按位置对」** —— 不同厂家的 8pin 顺序不一样，
> 有的模块 `VCC` 和 `GND` 是**反的**，照位置插会当场烧屏。
> 丝印别名对照：`SCL / CLK / SCK` · `SDA / DIN / MOSI` · `RES / RST / RESET` · `DC / RS / A0` · `CS / CE` · `BLO / BL / BLK / LED`

| 屏幕引脚 | ROCK 5B+ 40-pin | libgpiod 定位 | 说明 |
|---|---|---|---|
| **GND** | Pin 6 | — | |
| **VCC** | **Pin 1（3.3V）** | — | ⚠️ **严禁接 5V** |
| **SCL** | Pin 23 | SPI0_SCLK | |
| **SDA** | Pin 19 | SPI0_MOSI | |
| **CS** | Pin 24 | SPI0_CE0 | |
| **DC** | **Pin 18** | **`gpiochip4` line 20** | ✅ 实机 `gpiofind` 确认 |
| **RES** | **Pin 16** | **`gpiochip3` line 4** | ✅ 实机 `gpiofind` 确认 |
| **BLO** | **Pin 17（3.3V）** | — | 背光常亮；接 PWM 引脚可调亮度 |

> ✅ **GPIO 编号已在实机上用 `gpiofind` 确认**：`gpiofind PIN_18` → `gpiochip4 20`，`gpiofind PIN_16` → `gpiochip3 4`。
>
> ⚠️ **Pin 20 / 22 / 25 在这块板上不是 GPIO**（`gpiofind` 查不到），**不要用**。
>
> 💡 Pin 16/17/18/19 是连续的一段，接线最整齐。
> （D+ 引脚列表可用 `gpioinfo | grep PIN_` 查看，行名直接就是排针脚号。）

**Python（libgpiod v1.6，Debian 12 自带）用法：**

```python
import gpiod

# DC 和 RES 分别在不同的 gpiochip 上，所以要开两个 Chip
dc_chip  = gpiod.Chip('gpiochip4');  dc  = dc_chip.get_line(20)
rst_chip = gpiod.Chip('gpiochip3');  rst = rst_chip.get_line(4)

dc.request(consumer='st7789', type=gpiod.LINE_REQ_DIR_OUT, default_vals=[0])
rst.request(consumer='st7789', type=gpiod.LINE_REQ_DIR_OUT, default_vals=[0])

dc.set_value(1)     # 1 = 数据，0 = 命令
rst.set_value(0)    # 复位拉低，再拉高

# 用完记得 release()
dc.release(); rst.release()
```

> ⚠️ `gpiod` **不能 pip 装**（PyPI 版本要求 libgpiod ≥ 2.0，而 Debian 12 只有 1.6.3）。
> 必须 `sudo apt install python3-libgpiod`，并让 venv 能看到它（见第 9 节）。

> ✅ **不占用 Pin 8 / Pin 10**（系统串口控制台），两者不冲突。
> ✅ 屏幕上没有 MISO，所以 **Pin 21 空着**。

3. 自己写的好处：完全可控、没有外部依赖、排障时知道每一行在干什么

## 5. ⚠️ 性能：这是本子系统最大的技术风险

**每帧数据量**：

```
240 × 240 × 2 字节（RGB565）= 115,200 字节
```

### 5.0 实机速率扫描结果（2026-09-23 实测）

| 请求速率 | 实测推帧 | 实测帧率 | 有效吞吐 | 画面 |
|---|---|---|---|---|
| 10 MHz | 93.8 ms | 10.7 fps | ~9.8 MHz | ✅ 干净 |
| 16 MHz | 67.2 ms | 14.9 fps | ~13.7 MHz | ✅ 干净 |
| 20 MHz | 47.2 ms | 21.2 fps | ~19.5 MHz | ✅ 干净 |
| **24 MHz** | 48.6 ms | 20.6 fps | ~19.0 MHz | ⚠️ **比 20 MHz 还慢，禁用** |
| **30 MHz** | **39.2 ms** | **25.5 fps** | ~23.5 MHz | ✅ **干净 → 本项目采用** |
| 40 MHz | 29.8 ms | 33.5 fps | ~30.9 MHz | ❌ **直接黑屏** |

**三条结论：**

1. **本项目定 30 MHz** —— 25.5 fps，满足 20–30 fps 目标，画面完全干净。
   如果以后换模块 / 换线后出现偶发花屏，**退回 20 MHz**（21.2 fps）作保险档。
2. **24 MHz 是陷阱**：RK3588 的 SPI 时钟由固定时钟源**分频**得到，24 MHz 会被向下取整到
   **比 20 MHz 还低的一档**，实测反而更慢。**绝对不要用 24 MHz。**
3. **40 MHz 是"黑屏"而不是"花屏"**：SCL 超过 ST7789 的时序上限后，**初始化命令本身就收不到**，
   显示压根没被打开，所以是全黑。
   → 这是**非破坏性**的：下一次以 ≤30 MHz 重新初始化立刻恢复正常，**不会烧屏**。
   → 也正因为它是一条"断崖"而不是"渐变"，说明 30 MHz 离临界点还有余量，可以放心用。

**但音频处理必须实时（低延迟）——绝不能被屏幕刷新拖住。**

### 5.1 必须的双线程架构

```
┌─────────────────────────────────────────────┐
│ 音频线程（sounddevice 回调，小块 ≈ 5 ms）      │
│   采集 → 变声 → 播放                          │
│   顺便算：RMS 音量、FFT 频谱                   │
└──────────────────┬──────────────────────────┘
                   │ 只把「最新一帧数据」放进队列
                   ▼
        Queue(maxsize=1)，满了就丢旧的（关键！）
                   │
                   ▼
┌─────────────────────────────────────────────┐
│ 显示线程（独立线程，25 fps）                   │
│   取最新数据 → 渲染整帧 → SPI 推给屏幕         │
└─────────────────────────────────────────────┘
```

### 5.2 三条铁律

| # | 规则 | 违反的后果 |
|---|---|---|
| 1 | **显示线程绝不能阻塞音频回调** | 音频爆音、卡顿、掉帧 |
| 2 | **队列只保留最新一帧**（满了丢旧数据，不排队） | 显示延迟越积越大，最后滞后好几秒 |
| 3 | **照片必须在启动时预解码成 numpy 数组缓存** | 在渲染循环里 `Image.open()` 会直接掉到 2 fps |

> 补充：**FFT 不要放进音频回调**。虽然 2048 点 rfft 只要几十微秒，但回调里做任何非必要的事都是风险——放到显示线程里，从共享缓冲区取最新一段来算。

## 6. 频谱算法四要点

选**频谱**而不是波形，因为**变声改变的本质就是频率分布**——频谱能把它直接可视化（切到女声时高频段亮起来、低频段暗下去）。这是评委一眼能看懂的技术展示。

### ① 必须用**对数频率轴**（最容易被忽略）

人耳对频率的感知是对数的。线性分段会让几乎所有能量挤在前两根柱子里：

```
线性分段（❌）                  对数分段（✅）
├──┤ 0–1.5kHz 占 8 段          每段覆盖 ×1.4 倍频：
│  │  ← 能量几乎全挤在这         60 / 85 / 120 / 170 / 240 / 340 /
└──┘ 1.5k–24k 也是 8 段         480 / 680 / 960 / 1.4k / 1.9k / 2.7k /
        但几乎全是空的           3.8k / 5.4k / 7.6k / 10.8k / 15.2k
```

### ② 加**汉宁窗**，否则频谱泄漏

```python
spec = np.abs(np.fft.rfft(block * np.hanning(len(block))))
```

不加窗柱子之间会互相"串色"，看起来糊。

### ③ 转成 **dB**，不要用线性幅度

人耳也是对数的。线性幅度下弱频段完全看不见；转 dB 后动态范围好看得多。

### ④ 加**平滑 / 峰值保持**，否则柱子疯狂抖动

```python
bars = np.maximum(bars * 0.75, new_bars)   # 缓慢下落
```

不加这行，每帧数值乱跳，视觉上很廉价。

**参数建议**：2048 点 FFT（48kHz 下约 42ms 窗长）→ 频率分辨率 23.4 Hz；取 **16–20 个对数频段**。

## 7. 240×240 分屏布局

```
┌──────────────────────────────┐ 240px
│  ▁▃▅▇█▇▅▃▁▃▅▇█▇▅▃▁          │
│  频谱（16–20 段，对数轴）      │  ~85px
├──────────────────────────────┤
│                              │
│      有趣的照片 / 表情         │  ~115px
│      （启动时预解码缓存）       │
│                              │
├──────────────────────────────┤
│ 模式：女声   ▓▓▓▓▓▓░░░ 72%   │  ~40px
└──────────────────────────────┘
```

| 建议 | 原因 |
|---|---|
| **全屏重绘，不做局部更新** | 240×240 全刷也就 23ms，局部更新的复杂度不值得 |
| 频谱取 16–20 段 | 每段约 10–12px 宽，正好 |
| 照片预缩放到 **240×115** 并转 RGB565 | 运行时只做 `np.copyto`，极快 |
| 照片每 2–5 秒换一张，或按语音关键词切换 | 太频繁会显得乱 |
| 直接操作 **RGB565** numpy 数组 | 避免每帧做颜色格式转换 |
| 频谱柱用**渐变发光色**（低=蓝，高=红） | 保留原来"灯"的光效感 |

## 8. 常见故障排查

| 现象 | 大概率原因 |
|---|---|
| 完全黑屏，但背光亮 | 初始化序列没发对；`RES` 没接或没拉低复位 |
| 全黑且背光也不亮 | `BLO` 没接 3.3V；或 VCC/`GND` 接反 |
| 白屏 | `DC` 或 `CS` 接错（命令和数据没分开） |
| 花屏 / 雪花 | **SPI 速率太高**或杜邦线太长 → 先把速率降到 10MHz 试，稳定后再往上提 |
| 颜色反了（红蓝互换） | RGB / BGR 顺序设置不对，改初始化参数 |
| 只显示一条或半边 | `CS` 极性 / 屏幕偏移（240×240 有些需要设 offset） |
| 显示正常但很慢 | 每帧在做 `Image.open()` 或颜色转换 → 改成预缓存 + RGB565 |
